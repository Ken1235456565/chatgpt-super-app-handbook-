# Project Charter

## Purpose

Build a clear, maintainable website edition of **Understanding ChatGPT: Your AI Super-App for Work, Creativity, and Code**. The site should help a reader move from basic product orientation to practical work, software development, creation, verification, and responsible use.

## Primary audience

- Beginners who need a guided first success.
- Creators who work with writing, images, documents, websites, and research.
- Developers who use Codex, the CLI, IDE integrations, GitHub, and cloud workflows.
- Teams that need repeatable review, permissions, context, and governance practices.

## Source authority

Use this order when sources disagree:

1. The user's explicit instruction for the current task.
2. The linked Google document for the book's editorial intent and chapter structure.
3. Current official OpenAI documentation for product behavior, availability, commands, configuration, safety, and limits.
4. The checked-in Markdown edition for the currently published website copy.
5. The referenced CodexHandbook repository for information architecture inspiration only.

Do not copy the reference repository's branding, prose, analytics, or identity.

## Scope

The project includes:

- the 14 English handbook chapters;
- a reader-oriented homepage and chapter navigation;
- local copies of approved document images;
- search, accessible responsive layouts, metadata, sitemap, and deployment configuration;
- an auditable import and editorial workflow;
- rules for incremental maintenance.

## Non-goals

- Reproducing Google Docs layout pixel for pixel.
- Publishing every product detail without editorial prioritization.
- Creating a second documentation taxonomy that competes with the 14 chapters.
- Treating generated output as verified merely because it builds.
- Automatically deploying or pushing changes without approval.

## Definition of project success

The project succeeds when a reader can:

1. Choose a relevant path within one screen.
2. Find a topic through navigation or search.
3. Understand what to do, why it matters, and how to verify the result.
4. Distinguish stable concepts from changing product details.
5. Complete a small practical outcome without needing the source document open.
